# Harness Engineering：AI Agent 时代的系统工程核心

**Harness Engineering** 是 AI 应用技术演进的第三阶段，指除大模型本身以外，用于控制、引导和驱动 Agent 稳定运行的所有系统架构与支撑框架。其核心公式为：**Harness = Agent - Model**。这一概念由 OpenAI、Anthropic 等顶尖机构在 2024-2025 年的实战中系统化提出，标志着 AI 行业的研究重心从“如何与模型对话”转向“如何构建驱动模型的系统”。

## 与 Prompt Engineering、Context Engineering 的关系

Harness Engineering 是前两个阶段的自然演进：

| 阶段 | 核心技术 | 研究重点 | 目标 |
| :--- | :--- | :--- | :--- |
| **第一阶段** | **Prompt Engineering** | 研究如何把话对模型说清楚，侧重于提示词模板和组织方式。 | 提高单次回答的准确性。 |
| **第二阶段** | **Context Engineering** | 研究如何在合适的时间将合适的信息（对话历史、工具列表等）放入 Context。 | 解决模型记忆和特定信息获取问题。 |
| **第三阶段** | **Harness Engineering** | 研究如何围绕模型搭建一整套可运行、可校验、可自愈的系统（如权限管理、工具调用、自愈逻辑）。 | 实现 Agent 的长期、稳定、自动化运作。 |

**形象比喻：** 如果大模型是一匹强壮的野马，**Harness** 就是套在马身上的缰绳、头套和马鞍。没有这套“马具”，再强大的模型也会因为发散思维或幻觉而变成“脱缰野马”，无法转化为稳定的生产力。

## 行业巨头的实战案例

### 1. OpenAI：100 万行代码的疯狂实验
OpenAI 在 2024 年启动了一项实验：利用 AI 从零开始编写一个真实的线上生产系统。

- **核心成就：** 5 个月内生成约 100 万行代码，开发效率提升至纯人工的 10 倍。
- **Harness 优化策略：**
  - **上下文管理：** 放弃“大而全”的单一 `agent.md` 文档（避免模型在长文本中迷失），改为目录化结构，仅在需要时按需加载相关规范。
  - **唯一事实来源：** 强制将 Slack 记录、Google Doc 等碎片信息迁入代码仓库，确保 Agent 能感知仓库外的决策背景。
  - **验证与反馈闭环：** 为 Agent 配置 Chrome DevTools 截图验证 UI，并引入 Lint 和自动化测试。如果代码报错，错误信息会返回给 Agent 进行自愈式修复，无需人工干预。
  - **技术债清理：** 设置后台定时任务，由 Agent 自动扫描代码库和文档，清理不一致的命名或过时的文档。

### 2. Anthropic：长程运行 Agent 的 F-Harness 架构
Anthropic 针对长耗时任务提出了 **F-Harness（Framework Harness）** 方案，重点解决任务规划与质量评估。

- **多智能体协作模式：**
  1. **Planner（规划者）：** 将模糊的需求拆解为详细的功能点列表。
  2. **Generator（生成者）：** 按照列表逐一实现功能，并与评估者讨论交付标准。
  3. **Evaluator（评估者）：** 独立的第三方 Agent，负责客观检查产出，避免“自卖自夸”导致的 Bug 遗漏。
- **成本与效果对比：** 实验显示，Solo（单模型）方案耗时 20 分钟、成本 9 美元，但产品基本不可用；F-Harness 方案耗时 6 小时、成本 200 美元，但产出达到了可商用的高水准。

## 关键洞察与断言

### 1. 软件工程的职能演变
OpenAI 在其实践记录中提出了两个具有灵魂意义的观点：
- **"Human Steer, Agents Execute"（人类掌舵，Agent 执行）：** 人类工程师不再是一行行写代码的人，而是制定规则、提供上下文、在关键节点做判断的“掌舵者”。
- **工程师的新职责：** 软件工程并没有消失，而是演变为“为 Agent 搭建稳定可靠的系统与支撑框架”，以最大化代码产出效率。

### 2. 核心公式与定义
- **Harness = Agent - Model：** 这一公式界定了 Harness Engineering 的范畴——即研究除了模型本身以外的所有内容。

## 争议与未来趋势

### 争议点：新瓶装旧酒
批评者认为，Harness Engineering 涉及的 Lint 检查、任务拆解、自动化测试都是成熟的传统软件工程技术，该词汇只是 AI 圈造出的新噱头。

### 趋势点：模型能力的“吸收”效应
一个非常现实的趋势是：**模型越强，所需的 Harness 就越少。**
- **案例：** 当模型从 Claude 3.5 升级到 3.6（Opus 系列）后，原本为了解决“上下文焦虑”而设计的重置技术变得不再必要；原本需要强行干预的“逐个功能点执行”流程，也被模型更强的全局统筹能力所取代。

### 结论
Harness Engineering 虽可能不是最终的“终局答案”，但它是**当前阶段最现实的答案**。它是一座桥梁，连接着当前模型能力的局限性与未来通用人工智能的愿景。
