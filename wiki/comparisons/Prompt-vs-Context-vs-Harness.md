# Prompt vs Context vs Harness：AI 应用技术三阶段演进

AI 应用技术的发展并非线性爬坡，而是经历了三次范式跃迁。从 **“如何对模型说话”** 到 **“如何为模型准备信息”**，再到 **“如何为模型搭建系统”**，每一次跃迁都重新定义了工程师与 AI 的协作边界。本文基于 [[Harness Engineering：AI Agent 时代的系统工程核心]] 报告，系统对比这三个阶段的核心差异、技术重点与实战案例。

---

## 第一阶段：Prompt Engineering（提示工程）

### 核心命题
**如何把话对模型说清楚。**

在 LLM 能力尚不稳定、指令遵循能力有限的早期阶段，工程师的主要工作是设计精巧的提示词模板，通过角色设定、思维链（Chain-of-Thought）、少样本示例（Few-shot）等技巧，引导模型输出符合预期的结果。

### 技术重点
- 提示词模板化与版本管理
- 角色设定与语气控制
- 输出格式约束（JSON、Markdown 等）
- 思维链推理引导

### 局限性
- **无记忆：** 每次对话都是独立的，模型无法感知历史上下文。
- **无工具：** 模型只能基于训练数据回答，无法调用外部 API 或数据库。
- **无校验：** 输出质量完全依赖模型自身，缺乏自动化验证机制。

### 典型场景
- 单轮问答优化
- 文本摘要与翻译
- 简单的代码生成

---

## 第二阶段：Context Engineering（上下文工程）

### 核心命题
**如何在合适的时间将合适的信息放入 Context。**

随着模型上下文窗口的扩展（从 4K 到 128K 甚至 1M tokens），工程师开始关注如何管理对话历史、工具列表、知识库片段等动态信息，以解决模型的记忆局限和特定信息获取问题。

### 技术重点
- 上下文窗口管理（Token 预算分配）
- 检索增强生成（RAG）管道设计
- 对话历史压缩与摘要
- 工具调用（Function Calling）的上下文注入

### 关键突破
- 模型可以“记住”多轮对话中的关键信息
- 模型可以访问外部知识库（通过 RAG）
- 模型可以调用 API 执行具体操作（如查询天气、发送邮件）

### 局限性
- **无自主规划：** 模型仍然是被动响应，无法主动拆解复杂任务。
- **无自愈能力：** 一旦出现错误，需要人工介入修复。
- **无长期运行：** 上下文窗口有上限，长任务需要频繁重置。

### 典型场景
- 客服机器人（需记忆对话历史）
- 知识库问答系统
- 简单工具调用（如日历助手）

---

## 第三阶段：Harness Engineering（马具工程/系统工程）

### 核心命题
**如何围绕模型搭建一整套可运行、可校验、可自愈的系统。**

当模型能力足够强大（如 GPT-4、Claude 3.5+），瓶颈从“模型能力”转向“系统稳定性”。Harness Engineering 关注的是模型之外的所有支撑架构：权限管理、任务规划、工具编排、错误自愈、质量校验等。

### 技术重点
- **多智能体协作架构：** 如 Anthropic 的 F-Harness（Planner → Generator → Evaluator）
- **验证与反馈闭环：** 自动化测试、截图验证、Lint 检查
- **自愈逻辑：** 错误信息自动回传 Agent 进行修复
- **上下文目录化：** 放弃单一长文档，改为按需加载的模块化上下文
- **唯一事实来源：** 将 Slack、Google Doc 等碎片信息强制迁入代码仓库

### 核心公式
**Harness = Agent - Model**

即：Harness 是 Agent 系统中除去大模型本身以外的所有部分。它决定了 Agent 能否稳定、长期、自动化地运行。

### 实战案例

#### OpenAI：100 万行代码的疯狂实验
- **成就：** 5 个月内由极少数工程师主导生成约 100 万行代码，效率提升 10 倍。
- **Harness 策略：**
  - 放弃单一 `agent.md`，改为目录化上下文结构
  - 强制所有决策背景（Slack、Google Doc）迁入代码仓库
  - 配置 Chrome DevTools 截图验证 UI，引入 Lint 和自动化测试
  - 错误信息自动回传 Agent 进行自愈式修复
  - 后台定时任务自动清理技术债

#### Anthropic：F-Harness 长程运行架构
- **多智能体协作：**
  1. **Planner（规划者）：** 将模糊需求拆解为功能点列表
  2. **Generator（生成者）：** 逐一实现功能
  3. **Evaluator（评估者）：** 独立第三方 Agent 客观检查产出
- **成本对比：**
  - Solo 模式：20 分钟、9 美元 → 产品基本不可用
  - F-Harness 模式：6 小时、200 美元 → 可商用高水准

### 关键洞察
- **"Human Steer, Agents Execute"：** 人类从代码编写者转变为 Agent 系统的架构师。
- **工程师的新职责：** 为 Agent 搭建稳定可靠的系统与支撑框架，以最大化代码产出效率。

## 三阶段对比总表

| 维度 | Prompt Engineering | Context Engineering | Harness Engineering |
|------|-------------------|-------------------|-------------------|
| **核心问题** | 如何把话对模型说清楚 | 如何把信息放入 Context | 如何搭建驱动模型的系统 |
| **研究对象** | 提示词模板 | 上下文管理 | 系统架构与支撑框架 |
| **记忆能力** | 无 | 有（对话历史） | 有（持久化存储） |
| **工具调用** | 无 | 有（Function Calling） | 有（编排与自愈） |
| **自主规划** | 无 | 无 | 有（多 Agent 协作） |
| **自愈能力** | 无 | 无 | 有（错误回传修复） |
| **典型成本** | 低（秒级） | 中（分钟级） | 高（小时级） |
| **产出质量** | 单次回答准确 | 多轮对话连贯 | 系统级稳定可靠 |
| **工程师角色** | 提示词设计师 | 上下文管理员 | 系统架构师 |

## 演进趋势与争议

### 模型能力“吸收”效应
一个值得注意的趋势是：**模型越强，所需的 Harness 就越少。**
- 当模型从 Claude 3.5 升级到 3.6（Opus 系列）后，原本为了解决“上下文焦虑”而设计的重置技术变得不再必要。
- 原本需要强行干预的“逐个功能点执行”流程，被模型更强的全局统筹能力所取代。

### 争议：新瓶装旧酒？
批评者认为，Harness Engineering 涉及的 Lint 检查、任务拆解、自动化测试都是成熟的传统软件工程技术，该词汇只是 AI 圈造出的新噱头。

### 结论
Harness Engineering 虽可能不是最终的“终局答案”，但它是**当前阶段最现实的答案**——一座连接“模型能力”与“实际生产力”的桥梁。
